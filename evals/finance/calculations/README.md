# Finance Q&A calculations: MVP

Reuse existing calculator and agent tests rather than adding an evaluation
framework. `cases.jsonl` provides eight small labeled regression scenarios.

## Implemented

- Named calculator tool execution through the actual Finance Q&A agent graph.
- Preservation of explicit principal, rate, units, duration, APR/APY and frequency
  in validated tool inputs.
- Fixed expected balances and interest, including monthly/daily compounding,
  fractional years, decimal rates, APY without double compounding and cent rounding.
- Invalid simple-interest APY and unsupported fees produce errors without numbers.

Each record contains `id`, user `query`, `expected_tool`, normalized tool `inputs`
and `expected` output fields. Amounts are decimal strings, not floats. Six cases
have known arithmetic results; two must reject the request as specified.

The test model is scripted to emit the labeled tool and arguments. This verifies
execution and output handling, **not whether a live LLM selects the right tool or
extracts the right inputs from the question**. These same labels can support a
future live tool-selection run. Expected numbers are fixed teaching examples,
not generated by calling the calculator to build its own oracle.

## Existing coverage reused

- `tests/test_compound_interest.py`: APR/APY, defaults, frequencies, input validation,
  currencies, limits and rounding.
- `tests/test_simple_interest.py`: formula, decimal units, fractional years and
  invalid/missing inputs.
- `tests/test_calculation_agent.py`: real tool execution, clarification/resume,
  errors, retries, unsupported features, checkpoint persistence and labeled cases.
- `tests/test_simple_interest_agent.py`: simple tool execution, comparison of both
  methods, clarification limits and APY rejection.

```bash
pytest -q tests/test_calculation_agent.py tests/test_simple_interest_agent.py \
  tests/test_compound_interest.py tests/test_simple_interest.py
```

## Not implemented / future work

- Live LLM tool-choice and user-input extraction accuracy.
- Checking numbers in arbitrary generated prose against calculator artifacts.
- Additional calculators for loan amortization, portfolio returns or recurring
  contributions; these are outside the supported single-principal calculators.
- Separate scoring framework, LLM judge or live baseline for calculations.

Do not infer live model accuracy from the offline suite. Add future checks when
observed failures justify them. No production calculation logic is changed here.
